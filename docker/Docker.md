# Подготовка окружения
Выполните в своём терминале заранее.
```bash

# рабочий каталог для всех артефактов
mkdir -p ~/seminar4 && cd ~/seminar4

# --- проект hello (задачи 4 и 8) ---
mkdir hello && cd hello
cat > main.c <<'EOF'
#include <stdio.h>
int main(void) {
    FILE *f = fopen("data/input.txt", "r");
    char line[256];
    if (f && fgets(line, sizeof line, f)) printf("you said: %s", line);
    else printf("hello from image\n");
    fclose(f);
    return 0;
}
EOF
printf 'CC ?= cc\nCFLAGS ?= -O2 -Wall\nall: hello\nhello: main.c\n\t$(CC) $(CFLAGS) -o hello main.c\nclean:\n\trm -f hello\n' > Makefile
mkdir data && echo "world" > data/input.txt
cat > Dockerfile <<'EOF'
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y --no-install-recommends build-essential && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY Makefile main.c ./
RUN make
COPY data/ ./data/
CMD ["./hello"]
EOF
docker build -t demo-hello .
docker run --rm demo-hello
cd ..

# --- проект load (задача 9) ---
mkdir load && cd load
cat > cpuload.c <<'EOF'
#include <stdio.h>
int main(void) { volatile long x = 0; for (;;) x += 1; return 0; }
EOF
cat > memload.c <<'EOF'
#include <stdlib.h>
#include <stdio.h>
int main(int argc, char **argv) {
    unsigned long gb = argc > 1 ? atol(argv[1]) : 1;
    size_t n = gb * 1024UL * 1024UL * 1024UL;
    volatile char *p = malloc(n);
    if (!p) { fprintf(stderr, "alloc failed\n"); return 1; }
    printf("filling %lu GB...\n", (unsigned long)gb);
    for (size_t i = 0; i < n; i++) p[i] = 1;
    printf("held %lu GB\n", (unsigned long)gb);
    for (;;) {}
}
EOF
cat > Dockerfile <<'EOF'
FROM gcc:13
WORKDIR /src
COPY cpuload.c memload.c ./
RUN gcc -O2 -o cpuload cpuload.c && gcc -O2 -o memload memload.c
EOF
docker build -t demo-load .
cd ..

# --- каталог для bind-mount (задача 6) ---
mkdir -p shared && echo "from host" > shared/host.txt
echo "ГОТОВО: ~/seminar4"
```

> Примечание про `Makefile`: файл создаётся через `printf '...\t...'`, чтобы
> в рецептах Makefile гарантированно были настоящие табы (иначе `make` даст
> «missing separator»). Не переписывайте этот ряд вручную с пробелами.

## Задача 1. Установите Docker

### Условие

Установите Docker Engine, следуя **официальной инструкции Docker для вашей операционной системы**.

Не копируйте команды из случайных статей и форумов: в этой задаче важно научиться пользоваться официальной документацией инструмента.

После установки проверьте:
* доступна ли команда `docker`;
* какая версия Docker установлена;
* работает ли Docker Engine;
* удаётся ли запустить официальный тестовый контейнер `hello-world`.

На Linux при необходимости используйте знания о пакетных менеджерах с предыдущего семинара, чтобы проверить, какие Docker-пакеты были установлены.

### Инструменты

`docker`, `apt`, `dpkg`, `systemctl`, `man`

### Самопроверка

Команды:

```bash
docker --version
docker run hello-world
```

должны завершаться успешно.

## Задача 2. Поработайте внутри контейнера

### Условие

Запустите контейнер Ubuntu или Debian в интерактивном режиме и получите внутри него командную оболочку.

Уже **внутри контейнера**:
* определите текущего пользователя;
* посмотрите текущую директорию;
* исследуйте корень файловой системы;
* посмотрите информацию о дистрибутиве;
* создайте несколько директорий и файлов;
* запишите текст в файл и прочитайте его;
* установите `tree` через пакетный менеджер контейнера и запустите её.
* удалите `tree`

Откройте второй терминал на основной системе и убедитесь, что `tree` по-прежнему есть на host-системе.

Завершите shell контейнера и вернитесь в обычный терминал.

### Инструменты

`docker run`, `docker ps`, `bash`

Из предыдущих семинаров: `pwd`, `ls`, `cd`, `cat`, `echo`, `mkdir`, `touch`, `find`, `apt`

### Самопроверка

Убедитесь, что можете ответить:
* где сейчас выполняется команда — на host или внутри контейнера;
* почему пакет, удалённый внутри контейнера, не удалился в основной системе;
* является ли контейнер отдельной виртуальной машиной.

## Задача 3. Разберитесь с жизненным циклом контейнера

### Условие

До сих пор контейнер создавался и сразу использовался интерактивно. Теперь проследите за его жизненным циклом отдельно.

Создайте **именованный контейнер** и запустите в нём долгоживущий процесс.

Научитесь:
* смотреть только запущенные контейнеры;
* смотреть в том числе остановленные контейнеры;
* выполнять команду внутри уже работающего контейнера;
* останавливать контейнер;
* снова запускать его;
* перезапускать контейнер;
* удалять остановленный контейнер.

Внутри контейнера создайте:

```text
/tmp/marker.txt
```

и запишите туда произвольный текст.

Остановите контейнер, снова запустите его и проверьте файл.

### Инструменты

`docker run`, `docker ps`, `docker exec`, `docker stop`, `docker start`, `docker restart`, `docker rm`

Из предыдущих семинаров: `echo`, `cat`, `ls`

### Самопроверка

После последовательности:

```text
создать → изменить файловую систему → stop → start
```

`/tmp/marker.txt` должен сохраниться.

После удаления контейнера он больше не должен появляться в списке:

```bash
docker ps -a
```

Убедитесь, что понимаете различие между:
* остановить контейнер;
* запустить остановленный контейнер;
* удалить контейнер.

## Задача 4. Соберите собственный образ

### Условие

При ручной работе с контейнером окружение каждый раз приходится подготавливать заново. Опишите нужное окружение с помощью `Dockerfile`.

В материалах семинара находится готовая небольшая программа и Makefile. Изменять исходный код программы не требуется.

Создайте для проекта `Dockerfile`, который:
* использует готовый Linux-образ с необходимыми инструментами разработки;
* задаёт рабочую директорию;
* копирует проект внутрь образа;
* собирает программу;
* задаёт команду, запускаемую контейнером по умолчанию.

Используйте следующие инструкции Dockerfile:

```text
FROM
WORKDIR
COPY
RUN
CMD
```

Соберите образ и запустите из него контейнер.

После этого измените один из входных текстовых файлов проекта, снова соберите образ и обратите внимание на повторное использование уже выполненных этапов сборки.

### Инструменты

`Dockerfile`, `docker build`, `docker run`, `docker image ls`

Из предыдущих семинаров: `make`, `cat`, `vim`, `tree`

### Самопроверка

У вас должен появиться собственный образ, из которого запускается готовая программа.

Попробуйте своими словами объяснить различие между:
* Dockerfile;
* image;
* container.

## Задача 5. Проверьте, когда исчезают данные контейнера

### Условие

Создайте новый контейнер из собственного или стандартного образа.

Внутри него создайте:

```text
/data/important.txt
```

и запишите туда текст.

После этого последовательно проверьте несколько ситуаций.

1. Остановите контейнер и снова запустите его.
2. Убедитесь, что файл сохранился.
3. Удалите контейнер.
4. Создайте **новый контейнер из того же образа**.
5. Проверьте `/data/important.txt`.

Сравните результат с предыдущей задачей о lifecycle контейнера.

### Инструменты

`docker run`, `docker exec`, `docker stop`, `docker start`, `docker rm`

Из предыдущих семинаров: `mkdir`, `echo`, `cat`, `ls`

### Самопроверка

Вы должны наблюдать:

```text
stop/start контейнера
        ↓
данные сохраняются

удаление контейнера
        ↓
данные его изменяемой файловой системы исчезают
```

Сформулируйте, почему долговременные данные неудобно хранить только внутри контейнера.

## Задача 6. Подключите директорию host-системы в контейнер

### Условие

Создайте на host:

```text
~/seminar4/shared/
```

и несколько текстовых файлов внутри неё.

Запустите контейнер так, чтобы эта директория была доступна внутри него как:

```text
/shared
```

Проверьте обмен данными в обе стороны:
* создайте файл на host и прочитайте его из контейнера;
* измените файл внутри контейнера и посмотрите результат на host;
* создайте новый файл внутри контейнера;
* удалите контейнер и убедитесь, что данные в `~/seminar4/shared` сохранились.

После этого подключите директорию к новому контейнеру в режиме **только для чтения** и попробуйте изменить один из файлов из контейнера.

### Инструменты

`docker run`, `--mount`

Из предыдущих семинаров: `mkdir`, `echo`, `cat`, `ls`, `vim`

### Самопроверка

Изменения файлов через контейнер должны быть видны на host и наоборот.

После удаления контейнера содержимое:

```text
~/seminar4/shared
```

должно сохраниться.

В режиме read-only изменение файла из контейнера должно завершаться ошибкой.

## Задача 7. Сохраните данные в Docker volume

### Условие

Теперь сохраните данные так, чтобы конкретный путь на host выбирать не пришлось.

Создайте именованный Docker volume.

Подключите его к контейнеру как:

```text
/data
```

Создайте внутри `/data` несколько файлов и завершите работу контейнера.

Удалите контейнер.

Создайте новый контейнер и подключите к нему **тот же volume**.

Проверьте сохранность данных.

После эксперимента:
* посмотрите список существующих volumes;
* исследуйте созданный volume;
* удалите контейнеры, использующие его;
* удалите сам volume.

### Инструменты

`docker volume create`, `docker volume ls`, `docker volume inspect`, `docker volume rm`, `docker run`

Из предыдущих семинаров: `ls`, `cat`, `echo`

### Самопроверка

После удаления первого контейнера данные должны сохраниться в новом контейнере при подключении того же volume.

## Задача 8. Опишите рабочий контейнер с помощью Docker Compose

### Условие

В предыдущих задачах для запуска контейнера приходилось каждый раз указывать его образ, имя, директории и другие параметры в командной строке.

Перенесите конфигурацию такого рабочего контейнера в файл:

```text
compose.yaml
```

Используйте один сервис, представляющий среду разработки для подготовленного проекта.

В Compose-файле опишите:
* используемый образ или сборку из Dockerfile;
* подключение директории проекта;
* рабочую директорию внутри контейнера;
* команду, которая позволяет контейнеру оставаться запущенным.

После этого научитесь:
* создать и запустить контейнеры, описанные в `compose.yaml`;
* запустить их в фоновом режиме;
* посмотреть состояние;
* остановить;
* снова запустить;
* удалить контейнеры, созданные Compose.

### Инструменты

`compose.yaml`, `docker compose up`, `docker compose ps`, `docker compose stop`, `docker compose start`, `docker compose down`

Из предыдущих задач: `Dockerfile`, bind mounts

Из предыдущих семинаров: `vim`, `make`, `tree`

### Самопроверка

После:

```bash
docker compose up -d
```

контейнер должен появиться в:

```bash
docker compose ps
```

После:

```bash
docker compose down
```

созданный Compose-контейнер должен быть удалён.

Попробуйте объяснить, чем файл `compose.yaml` удобнее длинной команды `docker run` для регулярно используемого рабочего окружения.

## Задача 9. Ограничьте ресурсы контейнера

### Условие

Контейнер по умолчанию может конкурировать с другими программами за ресурсы host-системы.

**Запустите подготовленную в материалах семинара программу,** создающую CPU-нагрузку.

Во втором терминале наблюдайте использование ресурсов контейнером.

После этого повторите запуск, ограничив доступное контейнеру процессорное время.

Сравните результаты.

Аналогичным образом запустите подготовленный тест потребления памяти:

* сначала с достаточным объёмом памяти;
* затем с ограничением меньше необходимого программе.

Наблюдайте за состоянием контейнера и использованием ресурсов.

Не запускайте нагрузочные тесты без ограничений на длительное время.

### Инструменты

`docker run`, `docker stats`, `--cpus`, `--memory`, `docker ps`

Из предыдущих семинаров: `time`, `ps`

### Самопроверка

При ограничении CPU показатели контейнера и производительность workload должны измениться.

При слишком маленьком ограничении памяти программа не должна получить возможность бесконтрольно использовать память host-системы.

Убедитесь, что можете объяснить:

* имеет ли контейнер фиксированное количество CPU/RAM по умолчанию;
* зачем разработчику могут понадобиться resource limits;
* относятся ли эти ограничения к образу или к конкретному запуску контейнера.
